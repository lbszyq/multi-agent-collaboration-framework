# 项目规模适配指南

> 并非所有项目都需要全部框架文件（当前版本：46+ 个文档 + 10 个顶层脚本，另含 `tests/framework-selftest.ps1` 自测脚本）、12 个角色。根据项目规模选择合适级别。文件总数随版本增长，下表为核心文件约数，以仓库实际为准。

---

## 四级规模

| 级别 | 适用场景 | 角色数 | 核心文件数 | 预计工期 |
|------|---------|--------|-----------|---------|
| **Light** | 个人项目、原型验证、单次 demo | 3-5 | ~8 核心 + 4 角色文件 | 1-3 天 |
| **Light-AI** | 求职/实践级 Agent 项目（以六大标准为验收目标） | 4-6 | Light + Agent 最小集（约 12 核心 + 5 角色文件） | 3-7 天 |
| **Standard** | 中型商业项目、团队协作 | 6-9 | 完整文档体系（当前 46+ 文档 + 10 脚本） | 1-4 周 |
| **Enterprise** | 大型商业项目、多平台、合规需求 | 10-12 | Standard + ADR/独立契约/合规文档 | 1-6 月 |

---

## Light（最小启动集）

### 角色
```
R99 PM（编排）
R10 产品经理（需求 + 低保真原型）
R02 后端工程师（含数据库设计）
R04 前端工程师（含基础 UI 设计）
[R03 QA]（可选，小项目 PM 兼验）
```

### 文件（8 个核心 + 4 个角色文件）
```
AGENTS.md               ← 入口
README.md               ← 项目说明
docs/
  context-brief.md       ← 速览卡片
  project-status.md      ← 状态追踪
  architecture.md        ← 简化版（技术栈 + 模块拓扑 + API 契约即可）
  decisions.md           ← 关键决策
task-cards/
  template.md
reports/
  template.md
scripts/               ← 最小工具集（worktree/校验/巡检/状态/合并/一致性依赖，Light 不裁剪）
  framework-lib / new-task-card / new-worktree / validate-task-card /
  validate-report / patrol / generate-status / merge-card / scan-secrets / validate-framework
roles/
  R99 / R10 / R02 / R04  ← 仅激活的角色
```

### 简化内容
- 不需要 ADR（架构决策记录在 decisions.md 中）
- 不需要独立的 contracts/（API 契约直接写在 architecture.md 中）
- 不需要设计系统文档（R10 在 PRD 中直接描述页面）
- 不需要正式的变更管理流程（口头确认即可）
- **Worktree**：代码类任务卡一律使用独立 Worktree（含串行），主工作区归 PM 专用（`docs/git-workflow.md` §4）；Light 模式不豁免——`.\scripts\new-worktree.ps1` 一条命令即可创建并自动回填任务卡 front-matter

## Light-AI（AI 项目最小集）

> 面向求职/实践类 Agent 项目的推荐档位。以"高含金量 Agent 项目六大标准"（真实问题 / 工程体系 / 任务规划执行 / 上下文工程 / 评估监控 / 人机协同）为验收目标，在 Light 基础上补齐 Agent 专属治理，但不引入 Standard 的完整流程。

### 角色

```
R99 PM（编排）
R10 产品经理（需求 + 低保真原型）
R02 后端工程师（含数据库设计）
R04 前端工程师（含基础 UI 设计）
R09 AI 工程师（Agent/上下文/评估/可观测性/人机协同）
[R03 QA]（可选，小项目 PM 兼验）
```

### 文件（Light + Agent 最小集）

```
Light 的 8 个核心文件 + 4 个角色文件
+ docs/architecture.md §2 扩展（§2.2.1 运行时能力 / §2.9 上下文工程 / §2.10 可观测性 / §2.11 人机协同）
+ roles/R09-AI工程师.md
+ docs/templates/ai-evaluation-template.md（必选）
+ docs/templates/agent-observability-template.md（可选，任务含多步工具链时建议）
```

### 裁剪原则

- **不裁剪**：任务规划执行（§2.2.1）与评估（ai-evaluation）——这是 Agent 与非 Agent 项目的分界线
- **可简化**：上下文工程（单/双 Agent 可只做短期记忆）、人机协同（仅高风险操作必做确认节点）、可观测性（至少 trace_id + 工具成败埋点）
- **不引入**：ADR、独立 `contracts/`（契约写在 architecture.md 内）、设计系统文档、正式变更管理流程


## Standard（当前框架完整版）

即当前 `README.md` 描述的完整框架。适用于：
- 前后端分离的商业项目
- 需要 AI 能力的应用
- 需要 CI/CD 的项目
- 团队 > 3 人的协作

角色按需选择（见 R99-PM 角色推荐表），不需要全部激活。

---

## Enterprise（Standard + 增强）

在 Standard 基础上增加：
- 全面的 ADR（`docs/adr/`）——每个架构决策独立成文
- 详细的 API 契约（`docs/contracts/`）——每个模块独立契约文件
- 安全合规文档
- 测试计划文档
- Code Review 流程

---

## 如何选择

PM 在项目初始化（§0.1）时根据以下问题判断：

| 问题 | Light | Light-AI | Standard | Enterprise |
|------|-------|----------|----------|------------|
| 预计开发周期？ | < 1 周 | 3-7 天 | 1-4 周 | > 1 月 |
| 有几个平台？ | 1 个 | 1 个 | 1-2 个 | 3+ 个 |
| 是否有 AI 模块？ | 否 | 是（核心，单/双 Agent 级） | 可能有 | 核心依赖 |
| 是否需要 CI/CD？ | 否 | 否 | 可能需要 | 必须 |
| 团队规模？ | 1-2 人 | 1-2 人 | 3-5 人 | 5+ 人 |
| 是否有合规要求？ | 否 | 否 | 否 | 是 |

选择后，PM 在 `project-status.md` 中标注：`规模级别：[Light / Light-AI / Standard / Enterprise]`。

> **DSH 宿主默认档位建议**：DSH 下子代理上下文隔离成本高于 Codex（每个角色都要重读 docs 建认知），且子代理并发上限为个位数——因此 **DSH 项目默认选 Light / Light-AI 起步**，并按需合并角色（R05→R02 数据职责、R11→R04 基础 UI、R06 仅在有部署需求时激活），必要时再升 Standard。避免一开始就全量 12 角色 + 46+ 文档，否则初始化成本与 token 开销会让 DSH 用户难以承受。
