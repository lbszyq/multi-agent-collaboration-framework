# 需求变更管理流程

> 由 R99-PM 维护。解决"需求什么时候可以改、怎么改、改完之后怎么办"的问题。

---

## 一、核心原则

1. **冻结点之后改需求 → 必须走变更流程**，不可直接让执行者"顺便改一下"
2. **变更必有代价评估**：用户在确认代价前，PM 不派发任何变更任务
3. **变更闭环**：用户确认代价 → PM 出 CR 文档 → 按影响范围精准派发 → 只动受影响层，不级联重建

---

## 二、冻结点定义

每个阶段产出验收通过后，该产出物进入"冻结"状态：

| 阶段 | 产出物 | 冻结点 | 冻结人 |
|------|--------|--------|--------|
| 产品设计 | `docs/prd.md` | 用户确认 PRD 无误 | 用户 |
| UI/UX 设计 | `docs/design-system.md`、`docs/design/` | 用户确认设计规范无误 | 用户 |

> 设计冻结点后的重大变更（颜色/字体/间距/断点/核心组件），须先将当前版本归档到 `docs/design/history/design-v{N}.md`（按 `docs/design/history/template.md` 格式），再更新 `design-system.md`，并在 `decisions.md` 中记录决策。
| 前端原型 | 可交互原型（阶段一） | 用户在 R04 对话回复"原型确认" | 用户 |
| 架构设计 | `docs/architecture.md`、`docs/contracts/`、`docs/data-model.md` | PM 验收架构文档通过（含阶段一可行性评审） | PM |

> ⚠️ 架构冻结点之后，对 `architecture.md`、`contracts/` 的任何变更**必须通过 ADR**（架构决策记录）——不可仅走普通 CR 流程。ADR 写入 `docs/adr/` 目录，并在 `architecture.md` §14 ADR 索引中登记。
| 开发阶段 | 各模块代码 | 对应任务卡验收通过 | PM |

> **未冻结 → 可以改**（在当前阶段内，由当前角色直接调整）
> **已冻结 → 走变更流程**（必须经过 PM 评估、用户确认代价后才能改）

---

## 三、变更分级

PM 收到用户变更诉求后，首先分级：

### Level 0：即时修正（零流程）

**判定标准**（全部满足才算 L0）：

- [ ] 不改变任何已冻结文档的**实质内容**（功能范围 / 结构 / 字段 / 端点 / 语义）
- [ ] 不涉及数据库 schema 变更
- [ ] 改动范围在当前进行中任务卡的允许修改范围内

> **冻结文档内纯文字修正属 L0 例外**：已冻结文档中的错字、标点、排版等纯文字/格式修正不改变语义，不视为「改变已冻结产出物的实质内容」，可走 L0 直接修正；但须在 docs/decisions.md 记录一行（与 docs/轻量任务通道.md「未落盘 = 没发生」原则一致）。涉及语义/结构/字段/端点变更的，一律按 L2 处理。

**典型场景**：
- 文案错字修正、标点调整
- CSS 间距微调（在设计系统变量范围内）
- Bug 修复（不涉及 API/数据库 schema 变更）
- 日志级别调整、注释补充

**处理流程**：
```
用户提出 → PM 判定为 L0 → 直接在当前对话告知角色修改
                              （不需要 CR；PM 在 decisions.md 记录一行，落盘原则见 docs/轻量任务通道.md）
```

### Level 1：轻量变更（记录即可）

**判定标准**（全部满足才算 L1）：

- [ ] 不改变 PRD 中已确认的功能范围（不增删功能点）
- [ ] 不改变设计系统中已确认的布局/组件/交互流
- [ ] 不改变数据库 schema（不增删字段、不改字段类型）
- [ ] 不改变 API 契约（不增删端点、不改请求/响应结构）
- [ ] 改动范围可能超出**当前进行中任务的允许修改范围**


**典型场景**：
- 文案调整（按钮文字、提示语、页面标题）
- 颜色/间距/字体微调（在设计系统变量范围内）
- 单个组件的展示逻辑调整（不涉及数据流）
- Mock 数据的内容修改
- 非核心页面的结构调整

**处理流程**：
```
用户提出 → PM 判定为 L1 → 直接在 PM 对话中告知当前角色调整
                              → PM 在 decisions.md 中记录一条简要决策
```

### Level 2：重大变更（走正式 CR）

**只要满足以下任意一条**：

- [ ] 新增或删除功能点
- [ ] 调整业务流程或交互逻辑
- [ ] 改变数据库 schema
- [ ] 改变 API 契约
- [ ] 改变已冻结产出物的**实质内容**（PRD 功能范围 / 设计规范布局与组件行为 / 架构 / 契约的语义级变更；纯文字/格式修正除外，见 Level 0 例外）

**处理流程**：见第四节。

### 边界裁决

当 PM 无法确定级别时，**宁可升级**——宁可让用户多看一次代价确认，也不要低估影响。

---

## 四、Level 2 正式变更流程

```
用户提出变更诉求
       ↓
PM 分级判定 → Level 0/L1 则快通道
       ↓ Level 2
PM 生成 Change Request（CR-XXX）
       ↓
PM 逐层影响分析（见第五节）
       ↓
PM 输出"变更代价摘要"给用户
       ↓
用户确认 → 确认（接受代价）
       │
       ├── 接受 → PM 按影响范围生成修复任务卡 → 逐层派发
       │
       └── 拒绝 → CR 关闭，记录到 decisions.md，不做任何改动
```

---

## 五、影响分析矩阵

PM 逐层检查：这个变更是否影响到该层的已冻结产出？

| 层 | 检查项 | 需要看什么 | 受影响的角色 |
|----|--------|-----------|------------|
| **需求层** | 功能范围是否改变？ | `docs/prd.md` | R10 |
| **设计层** | 页面/组件/交互流是否改变？ | `docs/design-system.md`、`docs/design/` | R11 |
| **原型层** | 原型是否需要更新以反映新设计？ | R04 阶段一产物 | R04 |
| **架构层** | 模块划分、技术选型是否受影响？ | `docs/architecture.md` | R01 |
| **数据层** | 数据模型是否需要改动？ | `docs/data-model.md`（物理模型；逻辑模型见 `docs/architecture.md` §7） | R05 |
| **契约层** | API 接口是否需要增删改？ | `docs/contracts/*` | R02、R04 |
| **实现层** | 哪些已完成代码需要修改？ | `task-cards/archive/` 中的已归档卡 | R02、R04 |
| **测试层** | 哪些已有测试用例失效？ | `reports/` 中 R03 的测试报告 | R03 |

## 六、变更代价摘要格式

PM 输出如下格式给用户确认：

```markdown
## CR-XXX：{变更简述}

**来源**：用户在 {阶段} 提出
**变更内容**：{一句话描述}

### 影响范围

| 层 | 是否受影响 | 受影响角色 | 预计工作量 |
|----|-----------|-----------|-----------|
| PRD | ✅ / ❌ | R10 | X 轮对话 |
| 设计规范 | ✅ / ❌ | R11 | X 轮对话 |
| 前端原型 | ✅ / ❌ | R04 | X 轮对话 |
| 架构文档 | ✅ / ❌ | R01 | X 轮对话 |
| 数据模型 | ✅ / ❌ | R05 | X 轮对话 |
| API 契约 | ✅ / ❌ | R02 | X 轮对话 |
| 前端实现 | ✅ / ❌ | R04 | X 轮对话 |
| 后端实现 | ✅ / ❌ | R02 | X 轮对话 |
| 测试 | ✅ / ❌ | R03 | X 轮对话 |

### 代价总结

- **受影响角色数**：X 个
- **预计总工作量**：约 X 轮对话
- **当前进度影响**：已完成的任务卡 TC-XX、TC-YY 可能需要返工

### 替代方案（如有）

如果 PM 发现有更低成本的替代方案，在此列出：

- 方案 1：{描述}，成本 {X 轮对话}
- 方案 2：{描述}，成本 {Y 轮对话}

请确认：接受此变更（按上述影响范围执行）/ 拒绝此变更 / 选择替代方案 X
```

## 七、变更执行

用户确认接受代价后，PM 按影响范围**从上游到下游**逐层派发：

```
1. R10 更新 PRD（如受影响）→ 验收
2. R11 更新设计规范（如受影响）→ 验收
3. R01 更新架构/契约（如受影响）→ 验收
4. R05 更新数据模型（如受影响）→ 验收
5. R02 / R04 更新代码（如受影响）→ 验收
6. R03 回归测试 → 验收
```

> **原则**：只动受影响层，同级可并行。例如 PRD 没变但设计变了 → 只从 R11 开始，不动 R10。

## 八、CR 文档模板

每个 Level 2 变更写入 `docs/changes/CR-{序号}-{简述}.md`（目录规范见 `docs/changes/README.md`）：

```markdown
# CR-{序号}：{简述}

> **状态**：[pending / accepted / rejected / in_progress / done]
> **提出时间**：YYYY-MM-DD HH:MM
> **提出人**：用户
> **当前阶段**：{提出变更时项目所处的阶段}

## 变更内容

{用户原话 / 需求变更的具体内容}

## PM 分级判定

**Level**：[0 / 1 / 2]
**判定理由**：{为什么是 Level X}

## 影响分析

{填入第六节的影响分析表}

## 用户决策

**决策**：[接受 / 拒绝 / 替代方案 X]
**决策时间**：YYYY-MM-DD HH:MM

## 执行跟踪

| 任务卡 | 角色 | 状态 | 完成时间 |
|--------|------|------|---------|
| TC-XXX | R10 | done | YYYY-MM-DD |
| ... | ... | ... | ... |

## 关联记录

- 原任务卡：TC-XX、TC-YY（受影响的任务卡）
- 决策记录：D-XXX（写入 decisions.md 的决策编号）
```

## 九、异常场景

| 场景 | 处理 |
|------|------|
| 开发中期用户连续提出多个变更 | 每个变更独立走 CR 流程；多个 CR 之间有交集时，PM 合并为一张影响分析表 |
| 变更涉及正在进行中的任务卡 | PM 优先让当前角色完成（不中断），变更排在当前任务卡验收后执行 |
| 紧急变更（P0） | 暂停当前所有进行中任务，PM 快速评估影响 → 用户确认 → 立即派发 |
| 用户拒绝变更后又反悔 | 原 CR 文档状态从 rejected 改为 accepted，沿用之前的影响分析，如项目已有新进展则重新评估 |
| 变更导致已归档任务卡需要返工 | PM 新建修复类任务卡派给原责任角色（如对话已关则重开），不修改已归档的任务卡 |

## 十、与其他文档的关系

- `docs/decisions.md`：每个 accepted 的 CR 写入一条决策记录（D-XXX）
- `docs/project-status.md`：CR 执行期间更新阻塞项，影响分析中涉及返工的任务卡标记为 blocked
- `docs/architecture.md`：架构/契约变更由 R01 更新，PM 监督
- `docs/adr/`：涉及已冻结架构的变更，由 R01 产出对应的 ADR 记录（**R01 起草、PM 验收后 accepted**，重大选型经用户确认，见 `docs/adr/README.md`），并在 `architecture.md` §14 登记
- `PM-操作指南.md`：原型确认和最终验收章节引用本流程
- `docs/自动化协作协议.md`：异常处理表新增"需求变更"条目
