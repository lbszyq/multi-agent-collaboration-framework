# 存量项目接入清单

> 由 R99-PM 在把本框架接入**已有代码 / 已有 git 历史 / 已有部分文档**的项目时使用。空项目（从零开始）走 `docs/初始化清单.md`；存量项目走本清单。两者互斥，不要混用。
>
> **核心原则**：现状作为基线 + 债务显式化 + 只规范未来。框架接存量项目，目标不是改造历史代码，而是让后续增量协作可闭环、可追溯。

---

## 一、适用判定

| 场景 | 走哪个清单 |
|------|-----------|
| 空仓库、从零开始、无既有代码 | `docs/初始化清单.md` |
| 已有业务代码、已有 git 仓库、已部分开发 | 本清单 |

---

## 二、接入步骤

### 2.1 存量盘点

接入前先摸清家底，产出「存量资产清单」：

- [ ] 代码目录结构与技术栈（哪些是业务代码、哪些是构建产物/依赖）
- [ ] 已有文档（PRD / 设计稿 / 接口文档 / README / wiki 等碎片）
- [ ] 数据库 schema（表、字段、关系、索引）
- [ ] 对外接口（HTTP/RPC 端点、入参出参、错误码）
- [ ] 历史决策来源（commit message / issue / 聊天记录 / 口头）
- [ ] CI/CD、部署、环境配置

> 盘点决定「哪些回填进 SSOT、哪些放弃」。没有盘点就回填，容易把碎片当作真相。

### 2.2 SSOT 逆向回填（最重的一步）

框架的前提是「角色从 docs 建立认知」，存量项目必须先逆向产出 docs，否则框架转不起来：

- [ ] `docs/architecture.md`：从代码逆向模块拓扑 / 技术栈 / 分层 / 接口契约 / 错误码（§0.1 可行性评估与 §1~§11 逐章填写；AI 项目补 §2）
- [ ] `docs/prd.md`：从已实现功能回填 V1.0 范围（已上线的功能至少覆盖）
- [ ] `docs/data-model.md`：从数据库逆向物理模型（表结构/索引/迁移现状）
- [ ] `docs/decisions.md`：回填关键历史决策（为什么这么选型/这么设计）
- [ ] `docs/context-brief.md`：填入真实项目速览（一句话/技术栈/当前阶段）
- [ ] `docs/project-status.md`：填入当前阶段、冻结状态、规模级别

> **回填不是照抄代码，是提炼成契约与文档。** 逆向时一定会发现「代码实际行为」和「想记录的文档」不一致——此时以代码为现状、文档为目标契约，差异登记为债务（见 2.5），先允许并存，不强迫代码立即改。

### 2.3 Git 基线重建（保留历史，不做破坏性 init）

- [ ] **跳过 `git init`**——存量项目已有 git 历史，必须在现有仓库上操作，不得覆盖或重建历史
- [ ] 若尚无 `develop` 分支：`git branch develop`
- [ ] 主工作区切换到 `develop`：`git checkout develop`（主工作区归 PM 专用，见 `docs/git-workflow.md` §4）
- [ ] 将现有代码 + 回填的 docs 作为首个基线提交到 `develop`

### 2.4 代码纳入 `code/` 或声明例外

框架约定业务代码统一在 `code/` 下（`docs/architecture.md` §1.1）。存量项目按代价选择：

- 小项目 / 目录简单 → 搬迁到 `code/`，同步修正构建/CI 引用
- 大项目 / 目录耦合重 → **不搬迁**，在 `docs/architecture.md` §1.1 声明实际代码根目录为「例外」，后续任务卡路径以实际目录为准

> 框架约定不应该反过来伤害存量代码。搬迁是破坏性动作，收益低于风险时选择声明例外。

### 2.5 历史债务显式化（不硬套质量验收）

存量代码大概率不符合框架质量标准（缺测试、分层不干净、缺契约、错误码不规范）。**不要用 `docs/质量验收标准.md` 四层模型去验收存量代码**——那些 FAIL 是历史遗留，不是「新任务没做好」。

- [ ] 把存量代码的不规范，逐项登记到 `docs/architecture.md` §12 技术债务登记册（TD-XXX）
- [ ] 现状作为基线，新功能按新规范开发，债务按优先级逐步清理
- [ ] 债务清理通过「技术债务清理」任务卡派发，不顺手改

### 2.6 框架接管增量

- [ ] 完成上述回填后，运行 `.\scripts\patrol.ps1` 首次巡检（PASS / 记录 WARN）
- [ ] 后续新需求 / bug / 迭代走任务卡闭环（`docs/自动化协作协议.md`）
- [ ] 框架只规范「未来」，不负责「改造存量」——存量改造需求单独建卡、排优先级

## 三、常见错误

| 错误 | 后果 | 避免方法 |
|------|------|---------|
| 不逆向回填 docs，直接派卡 | 角色无 docs 可读，只能读代码瞎猜，产出不可控 | 先完成 2.2 再派卡 |
| 对存量代码硬套四层验收 | 全是历史遗留 FAIL，误伤无辜 | 存量债务走 2.5，只验收新增/变更部分 |
| 覆盖 git 历史重建仓库 | 丢失历史、无法追溯 | 保留现有仓库，只补 develop 分支 |
| 强行搬迁代码到 `code/` | 破坏构建/CI/引用 | 大项目声明例外，不搬迁 |
| 把代码现状当作目标契约 | 文档沦为「代码的说明书」，失去契约约束力 | 差异显式登记为债务，逐步收敛 |

---

## 四、与初始化清单的关系

- 空项目：`docs/初始化清单.md`（复制框架文件 + git init + 首次巡检）
- 存量项目：本清单（保留历史 + 逆向回填 + 债务显式化）
- 共同部分（规模级别、角色组合、质量裁剪、状态文档初始化）沿用 `docs/初始化清单.md` 第三至六节，本清单只补「存量特有」的步骤
