# contracts/ 目录

> 由 R01 架构师在此目录写入接口契约文件。

每个契约一个独立文件，命名规范：`{模块名}-contract.md`

此目录在项目初始化时为空，由架构师在架构设计阶段填充。

> **本文档 = 契约格式唯一权威**（`docs/architecture.md` §8.1 引用本文，勿双写）——R01 修改契约格式时只改本文件。

---

## 契约文件模板

每个契约文件（`{模块名}-contract.md`）按以下格式编写。每个端点独立一节：

```markdown
# {模块名} API 契约

> 版本：v1.0
> 最后更新：YYYY-MM-DD
> 维护人：R01-架构师

---

### POST /api/v1/{resource}

**说明**：一句话描述这个端点做什么

---

**请求**

POST /api/v1/{resource}
Content-Type: application/json

{
  "field_name": "value"
}

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| field_name | string | 是 | 字段说明 |

---

**成功响应**（HTTP 200）

{
  "code": 0,
  "message": "ok",
  "data": {
    "id": "xxx",
    "created_at": "YYYY-MM-DDTHH:MM:SSZ"
  }
}

| 字段 | 类型 | 说明 |
|------|------|------|
| data.id | string | 资源标识 |
| data.created_at | string | ISO 8601 时间戳 |

---

**错误响应**

{
  "code": 4001,
  "message": "具体错误描述",
  "data": null
}

本端点可能返回的错误码：

| 错误码 | 名称 | 说明 | HTTP 状态码 |
|--------|------|------|------------|
| XXXX | NAME | 描述 | XXX |

---

**约束**
- 业务规则 1
- 业务规则 2
```

> 契约文件产出后，PM 验收时会检查是否满足 `docs/architecture.md` §8.2 的检查清单。

## 设计 × 契约覆盖矩阵（design-contract-coverage.md）

> 由 R01 架构师在架构设计阶段产出，与 API 契约同步冻结。作用是防止「设计要、契约没、实现假装做」的三方断裂——每个设计交互点必须能追踪到数据源。

文件命名：`docs/contracts/design-contract-coverage.md`，模板如下：

```markdown
# 设计 × 契约覆盖矩阵

> 版本：v1.0
> 最后更新：YYYY-MM-DD
> 维护人：R01-架构师
> 依据：`docs/design/pages/` 页面规范 + 本目录 API 契约

---

## 使用方法

- 逐页对照设计规范的交互点（筛选、排序、搜索、分页、状态切换等），逐行登记
- **数据源**：填写对应的契约端点 + 字段；无数据源时填「无」
- 数据源为「无」的交互点，必须给出显式决策：`契约补字段`（走 CR 流程）或 `设计降级`（从实现范围移除/隐藏/置灰，并同步 R11 更新设计规范）
- 决策为「设计降级」的交互点，禁止实现方以假控件/假状态方式保留（如只渲染不生效的筛选器）

---
```
