# Codex 协作能力

> 本项目**默认手工协作模式**：PM 产出任务卡与派发文本块，由用户手动在侧边栏创建角色对话并粘贴派发；角色完成后在对话回报，用户转述给 PM 验收。自动化模式（宿主子代理工具）**实测在部分宿主不可用**，仅在有可靠 spawn/注入/等待能力的环境才启用。
> 编排能力来自宿主环境（如 Codex）的子代理工具，不依赖框架内置代码；本文档是这些工具的**操作语义说明**，具体操作步骤见 `PM-操作指南.md` §3。

---

## 可用能力（宿主工具映射）

> 下表为 Codex 侧工具名速查（语义动作与 DSH 对照、各动作的说明与使用时机见 `docs/dsh-capabilities.md`「术语速查」——通用映射唯一权威，不在此重复）。不同宿主工具名称可能不同，但语义一致：**唤起 / 注入 / 等待 / 关闭 / 复用**。

| 语义动作 | 宿主工具（Codex 示例） |
|---------|----------------------|
| 唤起子代理 | `spawn_agent` |
| 消息注入 | `send_input` / `followup_task` |
| 等待完成 | `wait_agent` |
| 关闭子代理 | （常驻，不关闭） |
| 复用子代理（常驻） | 不关闭 + `send_input` 续卡 |
| 文件系统 | 共享仓库 + 独立 Worktree（主工作区归 PM 专用） |

> **当前宿主工具映射（落地前先核对）**：上表工具名是**语义抽象**，不同宿主的前缀与命名可能不同（如当前 Codex 环境实际为 `collaboration__spawn_agent` / `collaboration__send_message` / `collaboration__followup_task` / `collaboration__wait_agent` / `collaboration__interrupt_agent` / `collaboration__list_agents`）。落地前先运行宿主提供的工具发现能力（`list_agents` 或系统提示工具清单）确认实际名称，不要按字面名猜。两个关键缺口及替代：
>
> - **关闭子代理**：常驻模型下**不主动关闭**，子代理生命周期随父会话存续。父 agent 重启后旧 agent id 失效，重新 `spawn_agent`（注入 `worker-init.md` + 任务卡，角色从 docs 恢复认知）。
> - **复用子代理（常驻）**：框架统一策略是「复用 = 常驻」——同一角色连续派卡时保持子代理 idle，用 `followup_task` / `send_message` 向既有子代理发新任务并触发 turn；关闭后不恢复，需要时重新 `spawn_agent`（注入 `worker-init.md` + 任务卡，角色从 docs 恢复认知）。
>
> **spawn 上下文隔离（两步派发，实测结论）**：宿主 `spawn_agent` 的 `fork_turns` 三档实测——`all` 继承全部历史（含「你是 PM」导致身份冲突）；`1` 继承最近一轮（仍带 PM 编排语义，诱导子代理套娃）；`none` 会连同 `message` 一起清掉（子代理收不到任何用户消息）。**因此不存在「隔离历史 + message 成第一条」的干净组合。正确做法是两步派发：**
> 1. `spawn_agent(fork_turns="none")` 拉起子代理，`message` 放空或占位——子代理醒来无用户消息，回「就绪，等待角色指派」；
> 2. 用 `followup_task` 注入「你是 R0X-岗位名 + 任务卡」——配合 AGENTS.md「最新身份声明优先」，子代理识别身份并开始执行。
> 执行者子代理必须遵守「执行者禁编排」硬约束（AGENTS.md），不得模仿上下文里的 PM 动作。

> **常驻模型（唤起后常驻，不关闭）**：
> - PM 按用户确认的角色组合**唤起角色子代理**（命名固定 `R0X-岗位名`），唤起后**保持常驻**，后续该角色的所有卡用 `send_input` 直接续派，**不关闭、不重新拉起**。
> - 子代理生命周期 = 父（PM）会话生命周期：父 agent 重启后旧 agent id 全部失效，角色按 AGENTS.md 从 docs 恢复认知后重新唤起。**上下文过长时由用户直接重启父 agent**（先落盘再重启，见 `PM-操作指南.md` §5），不靠关闭子代理管理上下文。
> 
> 高频**非业务**小任务（改文案、日志级别、配置值等，见 `docs/轻量任务通道.md` 通道 A）建议 PM 直接处理并落盘；**涉及业务代码的小修改（含小 Bug 修复）一律派卡**——用轻量卡（通道 B）派给常驻子代理。

### 常驻上下文协议

> DSH 宿主下同一协议以 `docs/dsh-capabilities.md`「常驻精简上下文协议」为准，且为 **DSH 默认建认知路径**（AGENTS.md 第三步 B 路径）；本小节为 Codex 宿主语义。

首次唤起时按 AGENTS.md 第三步「全量文档建立认知」；常驻后，后续每张新卡改为按需精读：

1. **必读**：`docs/context-brief.md` + `docs/project-status.md` + 当前任务卡 + `docs/thread-routing.md`（角色状态节）
2. **按需精读**：只在任务涉及时才读 `docs/architecture.md` / `docs/contracts/` / `docs/prd.md` / `docs/质量验收标准.md` 的相关章节（任务卡「约束与契约」会给出引用位置）
3. **保持常驻**：状态标 `idle`（见 `docs/thread-routing.md` 状态说明），PM 直接 `send_input` 注入下一张卡，不关闭

> 常驻协议只缩短「建认知」路径，不降低「执行」质量：契约、验收标准、回报格式等硬约束不变。子代理上下文随父 agent 生命周期存续，父 agent 重启后重新唤起并全量建认知。

## 环境依赖与边界（重要）

> **自动化编排是工作方式约定，不是框架内置的可执行模块。** 当前仓库不含编排层实现（没有拉起/注入/监听的代码），落地依赖宿主环境提供以下能力：

| 依赖项 | 说明 | 缺失时的后果 |
|--------|------|-------------|
| 子代理唤起 / 注入 / 等待 / 关闭 API | 宿主环境（如 Codex 子代理）必须能编程化创建角色子代理、注入消息、等待完成并关闭 | 只能退回手工模式（用户当信使） |
| 子代理并发上限 | 同时活跃的子代理数量受宿主环境限制（**通常为个位数**，以实际环境为准）；已关闭的子代理释放额度 | 无法一次性拉起全部角色，需按批排队 |
| 独立上下文 | 每个角色子代理上下文隔离，互不干扰 | 角色间共享上下文会串扰，违背"对话隔离"设计 |
| **agent id 生命周期** | 子代理 id 由唤起它的线程管理，**绑定当前线程**；PM 线程重启后旧 agent id 失效 | 重启后无法对旧子代理 send/wait/close，必须重新唤起 |
| **spawn 放行策略** | 宿主可能限制"何时允许自动唤起子代理"（如要求用户授权或任务卡授权） | 策略收紧时自动化流程受限，退回手工模式 |

**推论**：
- **手工模式是基线可用路径**——不依赖任何环境能力，任何环境都能跑
- 自动化模式下，并行角色数以宿主环境子代理并发上限为准；超过上限时分批派发或退回手工模式
- **PM 重启只保证"已落盘内容"可恢复**：docs / task-cards / reports / git commit 可恢复；未 commit 代码、子代理上下文、进行中的中间状态不可恢复。重启前应先让活跃子代理落盘中间状态（常驻模型下不 `close_agent`，父重启后子代理自然失效；详见 `PM-操作指南.md` §5）
- 框架的文档体系（SSOT + 任务卡 + 回报）在两种模式下完全一致，切换不损失能力

## 为什么默认手工模式

- **不依赖任何宿主编排工具**，任何环境都能跑，不会因 spawn/followup 行为差异而空转
- 用户当"信使"传递派发与回报，但 SSOT、任务卡、回报、验收闭环与自动化模式完全一致
- PM 对话丢失或上下文过长可重开，读取 `docs/` + `task-cards/` + `reports/` 可恢复已落盘的全貌
- 自动化模式仅在实测「spawn 能可靠注入身份+任务卡、wait 能可靠等待完成」的宿主才启用

---

## 手工模式（默认）

- 用户手动在侧边栏为每个角色创建对话，命名 `R0X-岗位名`，PM 输出派发文本块由用户粘贴传递
- 角色完成后在对话按固定格式回报，用户转述给 PM 触发验收
- 所有 docs 规则、任务卡、回报格式与自动化模式完全一致，切换不损失能力
