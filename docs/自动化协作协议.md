# 自动化协作协议

> **职责分工**：本文档 = 协作流程**协议唯一权威**（派发/回报/验收/异常/模型/Skill 规则）；`PM-操作指南.md` = PM 操作步骤手册（只写“怎么操作”，规则引用本文档）；`AGENTS.md` = 角色通用约束（启动/SSOT/安全红线）。修改流程规则时先改本文档，再同步操作指南与角色文件。高频规则唯一权威映射见 `docs/规则权威索引.md`。
> **宿主工具名**：本文档用「语义动作」（唤起/注入/等待/关闭/复用）描述编排，正文以 **DSH（默认宿主）工具名**落地——`subagent` / `send_message` / `list_agents` / `interrupt_agent`；Codex 宿主的两步派发与 `spawn_agent`/`followup_task`/`wait_agent` 等工具名差异见 `docs/codex-capabilities.md`，勿按字面名调用。术语速查见 `docs/dsh-capabilities.md`。
>
> 基于任务卡的任务分发、回报、验收闭环（**手工模式为宿主默认兜底**，自动化模式在可靠宿主能力下启用——DSH 已实测启用，见 `docs/dsh-capabilities.md`）。
> **环境依赖**：自动化编排依赖宿主环境提供子代理拉起/注入/监听能力。**DSH（DeepSeek Harness）宿主已实测可用**（`subagent`/`send_message`/`ask_user_question`/`pwsh`，见 `docs/dsh-capabilities.md`），自动化模式在 DSH 下可启用；部分宿主（如 Codex）的 spawn/followup 无法稳定把「身份+任务卡」送达子代理，退回手工模式。手工模式不依赖任何宿主能力，任何环境都能跑。详见 `docs/dsh-capabilities.md` / `docs/codex-capabilities.md`「环境依赖与边界」。
> 手工模式（Codex 等无可靠子代理能力的宿主默认）：PM 产出派发文本块，用户手动在侧边栏创建独立对话并粘贴；角色回报后用户转述给 PM。自动化模式（DSH 已实测，默认启用）：PM 用 `subagent` 一步派发、`send_message` 续派、`list_agents` 监听；子代理常驻不关闭，`interrupt_agent` 仅用于中断异常/超时，不用于验收后回收（见 `docs/dsh-capabilities.md`）。仅关键决策节点由用户决定——判定规则见 `PM-操作指南.md` §8：影响"做什么/花多少钱/什么时候好"的必须确认，影响"怎么做"的 PM 自主。

## 一、核心架构

│     ┌──────────────────────────────────┐     │

│     └──────────────────────────────────┘     │

        │             │             │

自动化模式：每个角色默认 = 一个由 PM 拉起的常驻子代理（独立上下文，可编程化注入任务卡/skill）；同一角色并行时按 §3.6「同一角色并行实例」例外执行；手工 fallback：每个角色 = Codex 侧边栏独立对话。

## 二、闭环流程

```
PM 更新 develop 并创建任务分支
（并行任务另行创建独立 Worktree）
    │
    ▼
PM 产出任务卡（写入 task-cards/，记录基线分支和基线提交）
    │
    ▼
PM 唤起角色子代理（spawn）：注入初始化消息 + skill + 任务卡
    │
    ▼
子代理读取 docs/ → 建立项目认知 → 执行任务
    │
    ▼
子代理完成 → 在对应工作目录提交代码和回报 → 按固定格式回报
    │
    ▼
PM 收到子代理完成通知（DSH 落定自动通知；无通知能力的宿主轮询 reports/）→ patrol 定位回报文件并验收
    │
    ├── 通过 → 合并到 develop → 更新 project-status.md → 产出下一张
    │
    └── 不通过 → PM 直接向子代理发出驳回指令（附原因）
```

## 三、详细操作步骤

### 3.1 唤起角色子代理（常驻）

**自动化模式（DSH 默认，一步派发）**：PM 按用户确认的角色组合，**唤起角色子代理**（命名固定 `R0X-岗位名`）——用 `subagent` 创建（`run_in_background: true`，prompt = worker-init 的「注入模板」（DSH 一步派发用法）「身份 + 认知路径 + 任务卡」，见 §3.2），配合 AGENTS.md「最新身份声明优先」识别身份并开工；按角色定义文件的「Skill 绑定」小节在 prompt 中注入 skill 引用（索引见 `roles/README.md`）。**唤起后保持常驻、验收通过后不关闭，后续卡用 `send_message` 续派（常驻模型）**。subagentId 登记到 `docs/thread-routing.md`（**唤起即登记，未登记不得派发**；运行时句柄用 `list_agents` 实时查询、不持久化），注意 subagentId 绑定当前 PM 线程，PM 重启后失效。

> Codex 宿主（两步派发，非默认）：`spawn_agent(fork_turns="none")` 空消息 + `followup_task` 注入身份与任务卡——实测差异与原因见 `docs/codex-capabilities.md`；无可靠子代理能力的宿主一律走下方手工模式。

**手工模式（fallback）**：用户在 Codex 侧边栏创建独立对话，每个对话按以下步骤初始化：

1. **对话命名**：`R0X-岗位名`（如 `R99-PM`、`R10-产品经理`）
2. **首条消息**：用户将角色初始化文本粘贴到对话
3. **角色对话回复"就绪"**后，等待任务卡

角色初始化文本 = `roles/templates/worker-init.md` 的「注入模板」代码块（唯一权威，不在此复制——避免多份拷贝漂移；回报文件格式唯一权威见 `reports/template.md`）。


### 3.2 派发任务卡

> **派发前置（P0）**：任务卡必须已 commit 到主工作区（默认 `develop`）并已由 `new-worktree.ps1` 校验「任务卡已进基线分支」——否则 feature Worktree 中找不到任务卡，验收/合并闭环断裂（见 `docs/git-workflow.md` §4.1 与 `scripts/new-worktree.ps1` 第 3.5 步）。

**自动化模式（DSH 默认，一步派发）**：① 用 `subagent` 拉起角色（`run_in_background: true`），prompt 直接包含「身份 + 认知路径 + 任务卡完整内容」（照抄 `roles/templates/worker-init.md` 的「注入模板」（DSH 一步派发用法），配合 AGENTS.md「最新身份声明优先」识别身份）；② 常驻角色的后续卡用 `send_message` 只发任务卡。代码类任务卡一律独立 Worktree（见 `docs/git-workflow.md` §4）。Codex 宿主的两步派发（`spawn_agent` 空消息 + `followup_task` 注入）见 `docs/codex-capabilities.md`，非默认路径。

**派发后落盘硬约束（未完成 = 不算派发完成）**：① 运行 `.\scripts\generate-status.ps1` 同步 `project-status.md`、`thread-routing.md` 自动生成区与 `context-brief.md`「当前活跃任务」（脚本自动完成三处）；② 在 `docs/thread-routing.md` 活跃对话表登记该角色状态并标 `working`（运行时句柄用 `list_agents` 查询，不持久化）。未同步 = SSOT 不一致，子代理会因状态冲突而无法可靠建立认知。

**手工模式（fallback）**：PM 产出"派发指令"文本块，由用户粘贴到目标角色对话：

```
→ 请将以下内容粘贴到 [R0X-岗位名] 对话：

---

执行任务卡：[粘贴 TC-XXX 完整内容]

开始前确认：
1. 进入任务卡 front-matter `workdir` 指定的独立 Worktree（代码类任务卡一律 Worktree；主工作区归 PM 专用，仅纯文档/纯配置卡可用主工作区并写明理由；规则见 `docs/git-workflow.md` §4）
2. 确认当前分支与任务卡 front-matter `branch` 一致
3. 确认当前提交包含任务卡 front-matter `base_commit` 指定的基线提交

完成后：
1. 按 reports/template.md 格式编写回报
2. 将回报写入任务卡工作目录的 reports/TC-XXX-回报.md（与代码一并提交）
3. 在对应 Worktree 提交代码和回报
4. 按固定格式回复任务卡、仓库根目录、工作目录类型、Worktree（如有）、分支、最新提交、工作区状态和回报文件（格式见 `roles/templates/worker-init.md`——完成信号格式唯一权威）
---
```

（手工模式：用户手动粘贴到对应的角色对话。）

### 3.3 监控角色进度

**自动化模式（DSH 默认）**：后台 subagent 落定时运行时**主动通知父线程**，PM 据此触发验收；无落定通知能力的宿主（如 Codex）用定期轮询 `reports/` 目录兜底。超时未回报时用 `send_message` 主动向子代理发提醒。

**手工模式（fallback）**：用户回到 PM 对话，转述角色的完整口头回报。

PM 收到完成信号后：
1. 根据回报中的工作目录类型、路径和分支定位实际工作目录；使用 Worktree 时再查询 `git worktree list --porcelain`
2. 读取 `reports/TC-XXX-回报.md` 并核对实际 Git 状态

### 3.4 验收回报

> **独立审阅预验收（大卡默认，缓解 PM 单点）**：大卡（涉及契约/schema/冻结产出物/外部证据项/多角色协作，见 `docs/质量验收标准.md` §6.1）在 PM 正式验收前，**默认**执行一次独立审阅——PM 用 `subagent` 拉起一个**新鲜上下文**的审阅子代理（不参与产出、不带 PM 的信任惯性），prompt 注入：回报文件实际路径（用 `patrol.ps1` 定位）+ 任务卡验收标准 + `docs/质量验收标准.md` 四层模型与 §1.2 证据责任矩阵 + 相关契约引用（prompt 可按需注入 `code-review` / `verification-before-completion` skill 引用）。审阅子代理要求：运行 `validate-report.ps1` 预校验、读取回报与相关代码、逐条核查验收标准、核对外部证据（含责任主体与可复核性）、输出「通过 / 不通过（问题清单）」。
>
> **结论处理**：独立审阅是 PM 仲裁的**输入**——不自动否决、不替代 R03 真实测试执行、不替代用户最终确认；PM 采纳（驳回/修复卡）或否决（记录理由）均写入 `docs/decisions.md`。涉及测试/契约密集的卡，PM 可指定 R03 角色实例担任审阅者（即原「R03 预验收」路径，并入本机制）。小卡 / light 卡豁免。

收到子代理完成回报（手工模式为用户转述）后：
1. 检查完成回报是否包含任务卡、工作目录类型、分支、最新提交、工作区状态和回报文件；使用 Worktree 时还必须包含 Worktree 路径
2. 缺少定位信息时，标记“定位信息不完整，暂不验收”，不得猜测代码位置
3. 根据工作目录类型定位实际目录；使用 Worktree 时通过 `git worktree list --porcelain` 核对，并执行 `git -C "<工作目录>" status --short --branch`
4. 检查工作区是否有未提交修改；有则不得通过验收
5. 读取 `reports/TC-XXX-回报.md`
6. 逐条核对验收标准的 [x]/[ ] 状态
7. 检查契约偏离（如有，评估影响并更新 `docs/architecture.md`）
8. 检查技术债务（如有，评估是否需要新任务卡）
9. 记录关键决策到 `docs/decisions.md`

**验收通过**：将任务卡 front-matter 状态标记为 `accepted`，然后由 **PM 执行合并**（`.\scripts\merge-card.ps1 -Card TC-XXX`，按 `docs/git-workflow.md` 合并到目标合并分支）；合并验证通过后将 front-matter 状态标记为 `merged`，再归档任务卡并运行 `.\scripts\generate-status.ps1` 更新 `docs/project-status.md` 与 `docs/thread-routing.md` 的自动生成区。

**不通过**：PM 直接向子代理发出驳回指令，附驳回原因（手工 fallback 下输出文本块由用户粘贴回角色对话）

**驳回收敛协议（防振荡）**：同一任务卡被驳回累计 ≥2 次仍未收敛时，视为**系统不稳定信号**而非普通质量问题——不得继续"驳回-重做"循环。PM 必须升级处置，三选一：
1. **重写任务卡**：驳回原因指向任务卡缺陷（范围不清 / 验收标准不可测 / 上下文不足）→ PM 重写任务卡后重新派发（驳回计数清零）
2. **换角色/换 skill**：原因指向执行能力或 skill 不适配 → 更换执行角色或注入不同 skill
3. **拆卡降复杂度**：任务过大导致不可验证 → 拆分为更小的卡分批验收
升级处置后再次被驳回（累计 ≥2 次仍不收敛）→ 升级为"拿不准"类决策节点，向用户汇报并请用户仲裁。每次驳回升级的处置理由由 PM 记入 `docs/decisions.md`。

### 3.5 状态边界

- `done`：角色声明实现完成，等待 PM 验收。
- `accepted`：PM 已完成实际 Worktree、代码、测试和回报核验，但尚未合并。
- `merged`：代码已合并到目标共享分支（由 PM 执行合并）。
- `accepted` 不是后续任务的默认基线；后续任务默认使用最新的 `develop`。
- 以上状态存于任务卡/回报文件头 YAML front-matter（唯一权威），`patrol.ps1` 与 `generate-status.ps1` 均以 front-matter 为准。
- 口头回报不是事实来源；它只提供验收入口和定位线索。
- 回报文件、Git 实际状态和口头回报不一致时，以 Git 实际状态为准，并记录异常。

### 3.6 并行派发

多张任务卡互不依赖且修改文件不重叠时，PM 可并行派发。**默认模型：每个角色只保留一个常驻子代理，该角色的多张卡用 `send_message` 顺序续派，不重复拉起**；跨角色的并行卡可各自拉起/复用其常驻子代理（各配独立 Worktree），分别注入任务卡并跟踪完成状态。同一角色确需并行时，按下述「同一角色并行实例」例外执行。并行任务分别验收后合并到 `develop`；发生冲突时暂停后续合并，按 Git 冲突流程处理。

**并行耦合检查（派发前必做）**：文件不重叠 ≠ 系统无耦合。并行派发前 PM 至少核对四条耦合通道，存在高耦合则不并行或显式定义协调顺序（串行化 / 锁定）：
1. **文件耦合**：各卡「允许修改范围」是否重叠（含测试文件、共享配置）——重叠禁止并行；派发前每张并行卡须在 front-matter 填写 `touched_files`（本卡将修改/新增的代码文件，逗号分隔，以 `code/` 为根），由 `patrol.ps1` 自动拦截重叠
2. **符号耦合**：各卡新增/移动/删除的导出符号（函数、类、Provider、模块导出等）是否被另一卡新增文件引用——被引用方有移动/拆分/删除时禁止并行，须先合并引用方再拆（任务卡「依赖关系」须写明导出符号）
3. **知识耦合**：各卡是否依赖同一份尚未冻结的 docs/ 契约、设计或决策——未冻结则串行化，已冻结可并行
4. **上下文耦合**：各角色是否需要共享同一设计语境——共享语境高时先派一张卡建立基线，再并行其余

**同一角色并行实例（例外）**：同一角色默认只有一个常驻子代理，不并行。仅当该角色有 ≥2 张卡，且顺序执行会造成可感知的关键路径阻塞（交付期限、下游依赖、长任务等）时，PM 可为该角色额外拉起临时子代理。必须同时满足：
1. 通过上述四条耦合检查；
2. 每张卡有独立 Worktree，文件范围不重叠（含测试文件/共享配置）；
3. 临时实例显式命名并登记，如 `R02-后端工程师#TC-007`，在 `docs/thread-routing.md` 标记为“临时并行实例”；
4. 该卡验收合并后，临时实例即回收/废弃，常驻实例保持唯一；
5. 拿不准是否值得并行时，默认串行。

**合并后验证（防交叉断链）**：并行卡或涉及符号移动/拆分的卡合并到 `develop` 后，PM 应在目标分支运行受影响范围的冒烟测试（`merge-card.ps1 -TestCommand "<命令>"`，如前端最小测试集 / 后端接口冒烟）。测试失败不自动回滚，PM 评估是否需要修复卡。

## 四、定期巡检（防漏报）

PM 在以下时机执行巡检：

1. **PM 启动时**：读取 `docs/thread-routing.md` + `reports/` 目录
2. **收到子代理完成回报时**：触发验收
3. **子代理落定通知 / 定期巡检**：DSH 依赖后台 subagent 落定自动通知；Codex 定期轮询 `reports/` 目录；发现新回报文件即验收，子代理长时间无响应时主动提醒

巡检检查项：
- `reports/` 是否有新回报文件未处理 → 直接读取验收
- 是否有任务卡超期未归档 → 检查对应子代理状态与回报
- 回报是否包含工作目录类型 / 分支 / 最新提交 / 工作区状态 → 缺失则要求补报
- 如果使用 Worktree，检查 Worktree 是否存在、分支是否匹配任务卡 → 不匹配则标记为异常
- 是否存在已验收但未合并到 `develop` 的分支 → 必须先处理或明确记录例外基线

**采样密度（离散控制视角）**：PM 巡检 = 对子代理状态采样。采样过稀会漏掉快速变化的状态（快速失败 / 快速完成）。按任务风险动态定采样频率：
- 高风险 / 长任务（预计复杂度=高，或预计工期长）：任务卡须填基本信息「检查点」字段，PM 在检查点主动向子代理轻量询问中间进度（`send_message`，不建卡）
- 低风险 / light 卡：一次等回报即可，无需中间采样

**禁止污染项目文件**：LLM 运行统计（token 用量、耗时、缓存命中率等）**禁止写入任何项目文件**（docs/、代码、配置）——项目文件只接受任务卡授权的产出；统计类信息仅出现在对话回报中。合并前 `merge-card.ps1` 对目标分支做工作区干净校验（merge-card.ps1 §3.1），发现脏数据先清理再合并。

## 七、模型策略

子代理默认继承父代理（PM）当前使用的模型与推理强度（宿主平台默认行为，无需配置）。

- 未填写任务卡「建议模型」/「建议推理强度」= 继承父代理模型，不使用任何全局推荐表
- 仅当任务确有特殊需求时，PM 通过任务卡「建议模型」/「建议推理强度」字段显式覆盖（如复杂架构推理用更强模型、纯文档任务用轻量模型）
- 框架不维护全局模型推荐表——任务间模型需求差异由 PM 按任务判断；未经真实成本数据校准的固定映射不具备参考价值

### 7.1 自适应校准（模型与环境变化 = 系统参数扰动）

子代理行为会随模型升级、上下文漂移、token 波动等因素不可预测变化——框架不做一次性固化，而是**定期校准**：
- **每完成约 10 张任务卡（经验节奏，可按项目规模调整）**，PM 汇总各回报 §9 度量信息，统计：驳回率、返工次数、平均实际轮数 vs 预计轮数、主要耗时环节
- 指标出现系统性偏差时调整（三选一）：任务卡质量要求（范围写法 / 验收标准可测性）、「建议模型 / 建议推理强度」选择规则、检查点密度
- 校准结论写入 `docs/decisions.md`（或 `docs/project-status.md`），不保留在对话中

## 八、Skill 策略与注入机制

> 自动化模式（子代理）与手工模式均适用。角色按**自己的角色定义文件**（`roles/R0X-*.md`）「Skill 绑定」小节获取对应 skill；全员通用规则（驳回反馈处理）已内联于 AGENTS.md 核心规则第 9 条，不依赖外部 skill。

### 8.1 优先级声明（不可违反）

```
项目约束（AGENTS.md / 任务卡 / docs/） > skill 工作方法
```

- skill 是"怎么做得好"的方法增强，**不是"做什么"的权威**
- 冲突时以项目约束为准；若 skill 与已冻结产出物（设计系统/架构/契约）冲突，在回报中标注，不自行按 skill 执行
- 设计类 skill（如 `design-taste-frontend`）仅在对应产出物未冻结阶段使用

### 8.2 注入机制

- **skill 来源**：各角色「Skill 绑定」写在其角色定义文件（`roles/R0X-*.md`）中；全员通用规则（驳回反馈处理）已内联于 AGENTS.md 核心规则第 9 条
- **自动化模式**：PM 拉起角色子代理时，按对应角色文件的「Skill 绑定」小节注入 skill 引用；任务卡「默认 skill」字段可覆盖
- **手工模式**：角色启动时按自己角色文件的 Skill 绑定，在宿主环境定位并加载对应 skill（定位与加载失败规则见 AGENTS.md 启动流程第二步）
- 任务卡可显式指定额外 skill（如 QA 类任务附加 `glm-vision-reader`）

### 8.3 成本约束

- 单角色默认绑定 skill ≤ 2 个，避免上下文膨胀
- 只按角色文件「Skill 绑定」表精选注入，禁止全量注入宿主 skill 清单
- skill 文件版本更新后，PM 在 `docs/decisions.md` 记录变更

### 8.4 加载失败处理

- 角色无法在宿主环境定位/加载绑定 skill（或任务卡指定 skill 不存在）→ 回报中明确标注"skill {名字} 加载失败"，由 PM 决定替换、豁免或降级为纯项目约束执行，**不静默跳过**
- `scripts/validate-task-card.ps1` **不校验 skill 绑定 / 「默认 skill」字段**（该字段是任务卡正文「基本信息（可选）」表格项，非 front-matter 字段，脚本不解析正文）——PM 建卡前应自行用宿主 skill 清单核对任务卡指定 skill 是否真实存在

### 8.5 对抗性审查（PM 关键节点）

> 解决「全体角色共享同一 SSOT、天然同向强化、缺少唱反调位置」的盲区。对抗审查不是否决权，是 PM 仲裁前的多视角输入。

- **触发时机**：冻结 PRD / 设计规范 / 架构与契约前，大卡（预计复杂度=高或涉及契约/schema/冻结产出物/外部证据项）验收前，以及重大方向决策前
- **执行方式**：PM 用 `llm-council` 对产出做多顾问独立分析 + 匿名互审，要求输出「最有力的反对理由 / 反例 / 未考虑的失败模式 / 替代方案」
- **结论处理**：委员会意见是 PM 仲裁的输入；PM 判定采纳（产出对应修复/调整卡）或否决（记录理由），结论写入 `docs/decisions.md`；影响「做什么 / 花多少钱 / 什么时候好」的仍属人类决策节点，由用户拍板
- **边界**：对抗审查针对「方案是否站得住」，不替代 R03 的质量/测试验收，也不替代用户的最终确认
