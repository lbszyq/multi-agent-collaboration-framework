# 轻量任务通道

> **状态**：已采纳（v1.0）
> **维护人**：R99-PM
> **目的**：解决「流程开销 > 任务本身」的问题——不是所有任务都值得走完整任务卡闭环（建卡 → worktree → 完整 9 章节回报 → 四层验收 → 合并）。为简单任务提供低摩擦通道，**防止流程被绕过导致 SSOT 失效**。

---

## 一、为什么需要

1. 完整闭环对简单任务（改文案、调日志、修单文件小 Bug）的成本远高于任务本身
2. 成本过高会诱导 PM/用户绕流程；一旦绕流程，SSOT 原则被击穿，整个框架从"严丝合缝"变成"文档是文档、现实是现实"
3. 本通道的验收原则：**让"走流程"永远比"绕流程"便宜**，同时保留追溯能力

---

## 二、适用判定（全部满足才走轻量通道）

- [ ] 不改变任何已冻结文档（PRD / 设计规范 / 架构 / 契约 / data-model）
- [ ] 不涉及数据库 schema 变更（不增删字段、不改字段类型）
- [ ] 不改变 API 契约（不增删端点、不改请求/响应结构）
- [ ] 不新增功能点（不含新模块 / 新页面 / 新接口 / 新业务流程）
- [ ] 改动文件数 ≤ 3 个，且不涉及多角色协作
- [ ] 不需要 R03 测试介入（无回归风险）

**典型场景**：文案错字修正、CSS 间距微调（设计 token 变量范围内）、日志级别调整、注释补充、配置值修改、单文件小 Bug 修复（不涉及契约/数据）。

**不适用（必须走完整闭环）**：新增/删除功能、schema 变更、契约变更、冻结产出物变更、跨模块/多角色改动、需要回归测试的改动、涉及外部证据验收项（T3/T7/U5/P8 等）的改动。

---

## 三、两个通道

### 通道 A：PM 直接处理（PM 可独立完成时）

| 项 | 内容 |
|----|------|
| 适用范围 | `docs/`、`task-cards/`、`reports/`、纯配置文件（CI 配置、`.env.example` 等）的单文件/少量修改 |
| 流程 | PM 直接修改 → 提交 → 在 `docs/decisions.md` 或 `docs/project-status.md` 记录一行（落盘） |
| 禁止 | 业务代码新功能、契约变更、schema 变更、需要多角色协作的改动 |
| 与「PM 禁止写业务代码」的关系 | 不冲突——通道 A 仅限文档/配置/非业务代码；业务代码一律派卡 |

### 通道 B：轻量卡（需要角色执行，但不必走完整闭环）

| 项 | 内容 |
|----|------|
| 建卡 | 用 `new-task-card.ps1 -Light` 建卡（front-matter `light: true`） |
| 简化内容 | 仅需「任务目标」「允许修改范围」（必填，精确到文件）「验收标准 1-3 条」；自动跳过 F3/F4 关键词提示（机器判定）。**章节结构保留**：模板各章节不删除，未涉及章节填「不适用」——`validate-task-card.ps1` 校验必填章节存在 |
| 工作区 | 默认主工作区（`workdir=主工作区` + `workdir_note=轻量通道（light 卡）`）；涉及代码类改动时 PM 判断是否仍需独立 worktree |
| 回报 | 只写 §1 总体状态 + §3 文件变更清单 + 完成信号定位信息，其余章节填「不适用（轻量通道）」 |
| 验收 | PM 抽查 + 轻量回报校验（不强制 4.2 外部证据清单完整格式） |

---

## 四、记录与追溯（SSOT 保持）

- 所有轻量通道改动**必须落盘**：通道 A → `decisions.md` 一行或 `project-status.md` 记录；通道 B → 轻量卡本身 + 一行回报
- **未落盘 = 没发生**（与主流程同一原则）
- 若轻量改动在执行中发现影响面比预期大（触及契约/冻结产出/多文件）→ **立即升级为完整任务卡**：补全验收标准，进入正常闭环，不允许"顺手继续改"

---

## 五、与现有机制的关系

| 机制 | 关系 |
|------|------|
| `docs/变更管理流程.md` L0/L1 | 轻量通道是「执行层」的轻量化，变更分级是「变更层」的轻量化。L0/L1 变更若同时满足第二节判定，可直接走轻量通道；L2 必须走完整 CR + 完整任务卡 |
| `docs/质量验收标准.md` | 轻量卡（`light: true`）自动跳过 F3/F4 关键词提示（机器判定）；不涉及【外部证据】项 |
| `docs/git-workflow.md` | 轻量卡不强制独立 worktree；通道 B 涉及代码类改动时，由 PM 按冲突风险判断是否建 worktree |

## 六、脚本支持（v1.0 已实现）

| 脚本 | 对 light 卡的处理 |
|------|------------------|
| `new-task-card.ps1 -Light` | 生成 light 卡（front-matter `light: true`），提示主工作区执行、无需 worktree |
| `validate-task-card.ps1` | `light: true` 时自动跳过 F3/F4 关键词提示（机器判定）；workdir 允许主工作区（仍需 `workdir_note` 理由） |
| `validate-report.ps1` | 回报 `light: true` 时只要求 §1 总体状态 + §3 文件变更清单，其余章节允许缺失或「不适用」；4.2 外部证据清单不适用 |
| `patrol.ps1` | light 卡不参与「代码类卡必须 worktree」交叉检查 |

> 字段契约：`light` 已加入任务卡/回报模板 front-matter（默认 `false`），字段清单唯一来源为 `framework-lib.ps1` 常量表（由 `validate-framework.ps1` 交叉校验）。

---

## 七、判定原则

**拿不准 → 走完整闭环。** 轻量通道是"降低合规成本的工具"，不是"逃避合规的后门"。宁可多花一点流程成本，不可丢失验收依据与追溯链。
